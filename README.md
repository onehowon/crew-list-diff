# CrewDiff — 선원명부 변경대조 도우미 (PoC)

선박대리점이 받은 **선원명부(IMO FAL Form 5) 최초본·수정본·수정 메일**을 FAL 5 항목으로 정리하고, 변경마다 **근거**와 **확인 필요 여부**를 보여 주는 신고자료 준비 도우미의 개념 검증(PoC)입니다.

- 해운 AX 공모전 출품용. **모든 인물·선박·번호는 가상**입니다(흔한 성·이름 조합, 형식만 흉내 낸 신분증번호, 검증 숫자를 일부러 틀리게 만든 IMO 번호).
- **신고를 전송하지 않습니다.** 출력은 담당자가 확인할 준비 자료입니다. KL-Net·정부 창구는 향후 연계 후보이며, 연동을 확인하지 않았습니다.
- 평가는 **대조·분류 엔진의 기능 성능**만 다룹니다. 현장 업무시간 절감은 주장하지 않으며 후속 PoC 과제입니다.

## 하는 일 / 하지 않는 일

| 하는 일 | 하지 않는 일 |
|---|---|
| CSV·TSV(엑셀 붙여넣기) 명부를 FAL 5 항목으로 정규화(셀마다 원문 줄·열 보존) | PDF·스캔 이미지 추출(실서비스에서는 LLM 추출 + 스키마 검증, 이 PoC 범위 밖) |
| 행 순서와 무관한 인물 대응(신분증번호 → 성명+생년월일 → 성명, 1:1) | 신고 전송·기관 시스템 연동 |
| 변경마다 **예상된 변경 / 확인 필요 / 오류 의심** 3단계 분류 + 근거 | 화물목록(FAL 2) 등 다른 서식(확장 계획) |
| 표기만 다른 것(대소문자·공백·날짜 형식·직급 약어·행 순서)은 경보하지 않고 접어서 개수만 | 과태료·벌칙 대상 여부 판단 |
| 변경 → 영향 받는 신고(출입국·세관·항만) 표시, 법령 원문 인용 | |
| 담당자 승인·보류 → FAL 5 순서 CSV, ECDSA P-256 서명 "변경 반영 확인서" | |

### 3단계 분류 기준
- `expected` 예상된 변경: **메일 지시 문장과 연결될 때만**(지시 줄 번호·문자 위치를 근거로 첨부).
- `suspect` 오류 의심: 규칙 R1~R8 중 하나라도 해당(규칙 id를 근거로 첨부).
- `check` 확인 필요: 그 밖의 모든 실질 변경. 근거가 부족하면 기본값.
- `cosmetic` 표기만 다름: 변경으로 세지 않음(경보 없음).
- 우선순위: 값 자체가 잘못된 규칙(R4·R6·R7)은 지시가 있어도 suspect → 지시 값과 수정본 값이 같으면 expected(R1~R3 모양이어도 정상 정정으로 보고 규칙은 참고로 표시) → 지시 값과 다르면 R8 → R1~R3 → 나머지 check.

| id | 규칙 |
|---|---|
| R1 | 문자 혼동: 같은 사람인데 신분증번호가 O↔0, I↔1, S↔5, B↔8, Z↔2 치환만으로 같아짐 |
| R2 | 일·월 뒤바뀜: 생년월일·만료일이 일·월 교환으로 같아짐 |
| R3 | 성명 순서 뒤바뀜(Family/Given 교환) |
| R4 | 신분증 만료일 < 입출항일 |
| R5 | 같은 사람이 한 명부에 두 번(신분증번호 또는 성명+생년월일) |
| R6 | 필수 항목 빈칸·판독 불가(???, #N/A 등) |
| R7 | 국적·발급국이 ISO 3166-1 alpha-3 아님, 생년월일이 입출항일 기준 만 16~75세 밖 |
| R8 | 메일 지시 미반영, 또는 반영된 값이 지시와 다름 |

## 평가

### 평가셋
- `eval/gen.mjs` 시드 20261020. 명부 120개(인원 15~25) → 수정본 쌍 200개(개발 140 · 홀드아웃 60), 라벨된 실질 변경 1,075건(개발 749 · 홀드아웃 326), 표기만 다른 셀 3,332개.
- 변경 종류: 예상된 변경(승선·하선·직급 변경·정정 반영, 메일 지시 있음), 지시 없는 실질 변경(직급·여권 갱신·출생지·무통보 승하선 → 정답 check), 오류 주입 R1~R8(→ suspect), 정상 정정인데 오류 모양(R1·R2 모양 + 메일 지시 → 정답 expected), 표기만 변경, 행 순서 섞기, 판독 불가.
- 레이아웃: 개발 D1(FAL 영문 CSV)·D2(탭, 약어 머리글, DD/MM/YYYY)·D3(세미콜론, DD-MMM-YYYY). **홀드아웃 H1(한국어 머리글·한국어 직급·YYYY.MM.DD·한국어 메일), H2(대문자 약어 머리글·MM/DD/YYYY·다른 영어 메일 문체)**. 사실 기록: H2 머리글 12개 중 `LAST NAME`·`BIRTH PLACE`·`SEX` 3개는 정규화하면 개발용(D3 Last name·Birthplace, D2 Sex)과 같습니다.
- 기준선1 "엑셀식 행 대조": 같은 행 번호끼리 셀 문자열 비교(앞뒤 공백 제거, 대소문자 구분), 다르면 모두 경보. 기준선2: 신분증번호 원문 문자열로 행을 맞춘 뒤 문자열 비교. 두 기준선 모두 엔진의 머리글 인식을 빌려 씀(기준선에 유리한 조건).
- 검수 범위 = 개별 확인 항목(엔진: suspect+check / 기준선: 모든 경보) ÷ 수정본 셀 수. **항상 "검수 대상에서 빠진 실제 오류 수"와 함께 보고합니다.**

## 개발 과정 기록(정직성)
git 이력으로 순서를 확인할 수 있습니다.
1. `9006e89` 엔진·머리글 별칭 사전을 평가 레이아웃 정의 **전에** 커밋.
2. 개발 세트로만 튜닝(`node eval/run.mjs`, 기본값이 개발 세트): 메일 속 이름 토큰을 **개수까지** 맞추도록 수정(예: `HOANG HOANG LONG`과 `DANG HOANG LONG` 혼동).
3. `21efbd7` 엔진 고정 후 홀드아웃 **1회 실행** → 결과를 `docs/eval-holdout-first-run.*`에 그대로 보존(대표값).
4. **홀드아웃 결과를 본 뒤 고친 것**(`1d304ba`):
   - 한쪽 버전에서만 인식된 열을 "열 없음"과 비교해 변경으로 잡던 버그(H1↔H2 쌍 오경보 345건의 원인). 이 수정으로 오경보는 0이 됐지만, 우연히 잡히던 국적 오류 1건이 놓침으로 바뀌어 놓친 오류가 2 → 3이 됐습니다.
   - 머리말 입출항일(ETA)과 메일의 숫자 날짜를 명부 날짜 열에서 추정한 일·월 순서로 해석(미국식 MM/DD/YYYY에서 R4 놓침·정정 오판의 원인).
   - **고치지 않은 것**: 머리글 별칭 사전. H2의 `NAT'Y`·`TRAVEL DOC.`는 여전히 인식하지 못하며, 그 열의 오류(R7 국적)는 놓칩니다. 화면은 "알 수 없는 열 머리글" 경고를 보여 줍니다.
5. 그 뒤 메일 머리 줄(From/Subject/제목 등)을 지시로 읽지 않도록 수정(데모 시나리오 3의 제목 줄 때문). 평가셋 메일에는 머리 줄이 없어 평가 수치는 바뀌지 않음을 확인했습니다.

## 한계
- 표 추출(PDF·스캔)은 하지 않으며, 메일 파서는 규칙 기반이라 생성기 문형(영어 2종·한국어 1종) 밖의 문체에서는 연결률이 떨어질 수 있습니다. 한 문장에 두 사람의 지시(예: "A relieved by B")는 연결하지 않습니다.
- 오류 유형과 비율은 설계자가 정했으며 실제 현장 분포가 아닙니다.
- 머리글 별칭 사전에 없는 약어는 열을 인식하지 못합니다(홀드아웃 `NAT'Y`, `TRAVEL DOC.`).
- R7은 ISO 3166-1 alpha-3만 정상으로 봅니다(ICAO 9303 여권 코드 `D`, `XXA` 등은 오경보 가능). 단일 이름(성 또는 이름이 없는 선원)은 R6으로 잡힐 수 있습니다.
- 확인서 서명 키는 저장소에 공개된 **데모 키**입니다. 실제 운영에서는 담당자별 키를 안전한 저장소에 둬야 합니다.
- 모바일은 최소 열람만 지원합니다(표는 가로 스크롤).
